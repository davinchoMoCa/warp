# Environment Git Mirror Cache — Technical Spec

Tracking issue: [REMOTE-3336](https://linear.app/warpdotdev/issue/REMOTE-3336/cache-environment-git-clones-on-warp-build-cache-root-via-a-typed).

## Summary
Reuse the Namespace build-cache volume to accelerate structured environment repository checkouts. A hidden, one-shot Warp/Oz CLI command owns the Git operations for cached and uncached runs. A cache failure must not make an otherwise valid checkout fail. Namespace must receive cache-path metadata for the new Git mirror directory.

## Behavior
1. On a Namespace run with a usable `WARP_BUILD_CACHE_ROOT`, each distinct structured source repository has a blobless bare mirror under `git-mirrors/<stable-key>`. A cold run populates the mirror from its canonical forge URL before checking out the repository. A warm run refreshes the mirror from that URL before checkout; it never serves an unchecked stale branch tip.
2. Every new working checkout remains independent of the mirror after preparation. Its `origin` points to the canonical forge URL, and no `objects/info/alternates` file points into the cache. Git may still fetch omitted blobs from the forge later, as with the existing blobless clone.
3. An unset cache root, a non-Namespace run, an unwritable volume, a missing or damaged mirror, or a failed mirror refresh uses the existing network-clone behavior. A missing mirror may first be populated; if that cannot complete, the checkout proceeds directly from the forge. A failed direct clone, fetch, or checkout remains a fatal environment setup error.
4. The same typed helper handles structured clones without a cache. Existing directory handling, SHA/ref pinning, `fetch_branch_only` substitution, parallel repositories, per-repository failure attribution, diagnostic output, resolved-HEAD snapshots, codebase indexing, and post-setup origin removal keep their existing behavior.
5. Git authentication continues through the session's credential helper. Neither the mirror's remote URL nor its key, metadata, command arguments, and diagnostics contain credential material. Mirror state remains scoped to the existing server-derived build-cache tag.
6. On a cache-enabled run with a Git mirror directory, Namespace's cache metadata describes `git-mirrors` without discarding metadata for build caches. Metadata failure is non-fatal and does not affect checkout correctness.
7. The Factory-definition repository clone remains the existing setup command. This feature changes only structured environment repositories.

## Technical design
### Typed checkout command
- Add a hidden `environment-checkout` CLI command to `CliCommand` in `crates/warp_cli/src/lib.rs`. Define `--requests-base64 <base64url-json>` and `--failure-report <path>` in `crates/warp_cli/src/environment_checkout.rs`. Dispatch it without login, run ID, or server API initialization in `app/src/ai/agent_sdk/mod.rs`; make the command one-shot and available on Linux and macOS. Update exhaustive CLI tracing/telemetry matches without recording repository names or URLs.
- The driver serializes validated `RepositoryCloneRequest` values as a versioned JSON batch encoded into one URL-safe base64 argument. Include forge, owner, repository, checkout name, head kind/value, `fetch_branch_only`, and working directory. Do not serialize credentials or arbitrary clone URLs. The helper reconstructs the URL with `SourceRepo::https_clone_url()`. Shell-quote the executable path and every argument; the base64url payload contains no shell metacharacters. Reject invalid encoding, unsupported forges, invalid repository identities, and duplicate checkout targets before starting work.
- Resolve the executable from the running Warp/Oz process, not an unverified `warp` in `PATH`. Invoke it through the active session's `TerminalDriver::execute_command`, so Git inherits the session's home, credential store, and sandbox filesystem. If the executable is not reachable or the helper cannot start, report a clear setup failure; do not silently run the old shell script. Cover Linux container and macOS app-bundle executable paths.
- Move both single-repo and parallel-repo Git logic from `environment.rs` into a small app-owned module with typed request and Git-process adapters. Use a bounded worker pool for distinct repositories; only one worker may update any one stable mirror key per batch. Capture output per repository and print it in request order, including existing progress messages. Return a typed per-repository failure report through a session-local temporary file that the driver reads through the silent executor and removes. Preserve the existing `PrepareEnvironmentError` clone/checkout categories, output redaction/truncation, and credential-identity diagnostics. Do not put raw tokens or a credential-bearing URL in the report.
- Keep request preparation, `SetupStep::EnvironmentRepoClone`, resolved-HEAD snapshot capture, index registration, build-cache setup, setup commands, and origin removal in the current order. The helper only materializes repositories; it does not own environment-wide setup.

### Mirror lifecycle
- Add one function that resolves an optional Git-mirror root. It checks Namespace isolation, the cache-root environment variable, and an accessible writable directory. The remainder of the checkout code accepts `Option<&Path>`; changing to a separate volume later changes only root resolution. Never write to `repos/` or `shared/`.
- Compute `<stable-key>` from the canonical forge host, owner, and repository with `RepoIdentity`/`RepoCacheKey`; key the **source** repository after any `clone_from` substitution. The hash excludes refs, checkout paths, user IDs, and secrets. Reject path traversal and symlink escapes under `git-mirrors/`. Cache reuse is confined to the server-scoped volume.
- For an absent mirror, create a blobless bare mirror against the canonical HTTPS forge URL in a temporary sibling directory. Validate it as a bare repository, set/verify its origin to the canonical credential-free URL, and publish it only after a successful fetch. For an existing mirror, verify it is bare with the expected remote and required promisor/filter configuration, then fetch/prune from that remote before use. A failed validation or fetch triggers a rebuild in a temporary sibling directory. Do not use a mirror until the replacement is complete; if replacement fails, perform a direct network clone. Do not use stale refs after a failed refresh.
- Seed the working checkout using the mirror as an object source while retaining the canonical forge URL as `origin`. Fetch requested refs from the forge when the existing semantics require it, then detach to freshly fetched `FETCH_HEAD`; do not resolve from a stale local branch. For `fetch_branch_only`, preserve the default-branch alias and single-branch fetch refspec. For an existing target, preserve today's skip/fetch behavior without replacing the directory or reading unrelated cache objects.
- Dissociate before reporting success: repack borrowed reachable objects into the checkout and remove/verify the absence of `objects/info/alternates`. Preserve `--filter=blob:none`, promisor configuration, tree availability, and lazy blob fetching. If a cache-backed attempt fails before a new checkout is complete, remove only its newly created staging checkout and retry once directly from the forge. A failed direct attempt is fatal; do not delete or overwrite a pre-existing target.
- Emit bounded categories for cache hit, cold population, invalid/rebuilt mirror, cache failure with network fallback, and fatal direct checkout. Do not log raw cache paths, remotes, credentials, or the serialized batch. Do not add cross-run `flock`: Namespace instances receive private forks of the CACHE volume.

### Namespace usage metadata
- On a Namespace run, after the existing build-cache setup step and before user setup commands, merge a `git-mirrors` entry into `<WARP_BUILD_CACHE_ROOT>/.ns/cache-metadata.json` if the directory exists. Emit the canonical protobuf JSON field names for `CacheMetadata` version 1: `version`, `updatedAt`, and `userRequest`. The entry has `source: "warp"`, `cacheFramework: "git"`, and `mountTarget: []` (working checkouts are copies, not mounts). The map key is the volume-relative path `git-mirrors`, not an absolute path or a per-repository key. Accept either the camelCase or the protobuf snake_case spelling when reading an existing file, without creating a second map. Update the timestamp in UTC on a successful merge.
- Preserve all other metadata entries and unknown fields, including entries written by `spacectl`; do not replace the whole map. Create `.ns` and the document if absent. Read/modify/write through a same-directory temporary file and atomic rename. If the existing document is malformed, has an unsupported version, or is a symlink, warn and leave it unchanged. A write failure is non-fatal. Do not write metadata when caching is disabled or no mirror directory exists.
- No `warp-server` code change or new Namespace volume is needed: this is a file inside the already attached volume. Namespace reads its path usage to track Git-versus-build-cache utilization. Verify the final file after `spacectl` cache setup rather than assuming another tool preserves it.

## Decisions
- **Volume:** Reuse `WARP_BUILD_CACHE_ROOT/git-mirrors/` now. A dedicated `NSC_GIT_MIRROR` volume isolates capacity but adds provisioning and tagging work; one optional-root function preserves that later option. Approved by the requester.
- **Checkout engine:** Move every structured environment checkout into the hidden typed helper. Keeping the shell code for uncached runs would create two implementations of ref and failure semantics; the broader migration needs regression coverage. Approved by the requester.
- **Freshness and failure:** Populate cold mirrors, refresh warm mirrors, and fall back to direct network fetch/clone after a cache failure. Serving stale refs saves network calls but violates requested pin/default-branch behavior. Approved by the requester.
- **Helper failure:** Fail clearly when the executable itself cannot run. Falling back to the old shell snippet would retain an untested, divergent engine; only cache problems fall back to network Git. Approved by the requester.
- **Capacity:** Write Namespace `CacheMetadata` instead of a bespoke disk-usage counter. This allows Namespace to report path utilization from the shared 20 GiB volume. The requester asked for this change; eviction and resizing remain separate work.
- **Factory definition:** Keep its credential-bearing setup-command clone out of this batch. Integrating it needs a distinct secret-safe input and compatibility path for persisted environment commands. This exclusion was approved by the requester.

## Assumptions
- Metadata entry values `source: "warp"` and `cache_framework: "git"` and an empty `mount_target` represent an unmounted mirror directory under the published `CachePathUsage` schema. Confirm the path appears under Namespace's path-utilization report during staging validation; if Namespace rejects this representation, revise the spec before implementation proceeds.
- The running Warp/Oz executable is reachable from the terminal session on supported Linux Namespace images and macOS Namespace app bundles. The implementation must test this rather than assuming host paths map into a nested container.
- Metadata preservation is possible because the checkout, existing build-cache setup, and final metadata merge run sequentially in one environment-preparation flow. No cross-instance file lock is needed.

## Out of scope
- A dedicated Git-mirror volume, cache-size increase, mirror eviction policy, and performance guarantee. Namespace may return older generations or reset an oversized cache; observed usage and measured clone timings should inform later changes.
- Caching the Factory-definition setup command, arbitrary user setup-command clones, Git LFS objects, and recursive submodules. These are separate clone flows or optional Git features, not structured environment repositories.
- Rendered UI changes or computer-use proof. This is a CLI and cache behavior change.
